Breaking Privacy in Federated Learning

IA-1 · Problem Formulation and Preliminary Implementation · Suyash Humne (16014223085)
Abstract. Federated learning (FL) is widely promoted on the premise that "data never leaves the device" — participants share only model gradients, not their raw data. This project interrogates that premise directly. We implement a gradient-inversion attack in which an honest-but-curious server reconstructs a client's private training image, pixel-by-pixel, from the single gradient the client uploads. Using the cosine-similarity gradient-matching method of Geiping et al. (2020) with total-variation regularisation and analytic label recovery (iDLG), our attacker correctly recovers the private label and reconstructs the image at 24.53 dB PSNR from only 19,438 gradient values, with no access to the pixels. The attack is the lens through which the five course modules are unified: it motivates and is measured against the privacy defences of Differential Privacy (Module 2), Local Differential Privacy (Module 3), Privacy-Preserving Data Mining / anonymity (Module 4) and Compressive Privacy (Module 5), with Module 1 providing the threat model. This IA-1 report establishes the problem, maps it to all five modules, prepares the dataset, and demonstrates the working attack as the preliminary implementation; IA-2 completes the defence comparison and evaluation.

1  Problem Definition and Significance

1.1  Context and motivation

Machine learning increasingly trains on data that is legally and ethically sensitive — medical records, financial histories, biometric images. Federated learning (McMahan et al., 2017) was introduced precisely to make such training privacy-respecting: instead of centralising raw data, each participant (a hospital, a phone, a bank) keeps its data locally, computes the gradient of the shared model's loss on that local data, and transmits only the gradient to a central server, which aggregates the gradients to update the global model. The marketing claim is simple and appealing: your data never leaves your device.

The security question this project asks is equally simple: is a gradient actually safe to share? A gradient is a deterministic function of the private data and the known model parameters. If that function is even partially invertible, then "sharing a gradient" leaks "sharing the data" — and the entire privacy argument for federated learning collapses. This is not a hypothetical: the 2019–2022 literature on deep leakage from gradients established that gradients can be inverted to recover training inputs with alarming fidelity.

1.2  Problem statement

Given a neural network with known architecture and parameters, and the gradient of its loss computed on a client's single private training example, can an honest-but-curious server reconstruct that private example (its pixels and its label) without ever observing the data — and which privacy mechanisms from the course syllabus can measurably prevent or degrade this reconstruction, and at what cost to model utility?

1.3  Objectives

  1. Attack. Implement a working gradient-inversion attack that reconstructs a private image and recovers its label from a shared gradient, in a simulated federated-learning setting.
  2. Quantify. Measure reconstruction fidelity with standard image-quality metrics (MSE, PSNR, SSIM, LPIPS) and extend the attack from a single image to small batches to map its limits.
  3. Defend. Implement and evaluate four defence families drawn from the five syllabus modules — differential privacy, local differential privacy, compressive (sparsification / quantization) privacy, and anonymity-based aggregation — against the same attack.
  4. Trade-off. Characterise the privacy–utility trade-off of each defence: how much reconstruction quality falls versus how much model accuracy is sacrificed.
  5. Corroborate. Add a second, complementary privacy attack (membership inference, LiRA) to measure leakage quantitatively and to audit the differential-privacy guarantee empirically.

1.4  Scope and expected outcome

The scope is the honest-but-curious server threat model on image data (CIFAR-10 as a public, reproducible stand-in for private image data such as medical scans). Malicious-server attacks that modify the model architecture (e.g. Robbing the Fed) are discussed analytically and used for cross-validation but are out of the implementation scope for IA-1. The expected outcome is a reproducible benchmark showing (a) that gradient sharing leaks private data, and (b) a ranked, measured comparison of the syllabus defences against that leak. This is, to our knowledge, not available as a single unified study across all four defence families under one attack — which is the individual research contribution (Section 7).

3  Conceptual Understanding and Methodology

3.1  Why a gradient leaks data

For a model with parameters θ and loss L, a client holding a private example (x, y) uploads the gradient g = ∇θL(fθ(x), y). The attacker knows θ, f and L, and receives g. It reconstructs the input by searching for a synthetic image x̂ whose gradient ĝ best matches the observed g:

x̂* = arg minx̂   D(∇θL(fθ(x̂), ŷ),  g)  +  α·TV(x̂)

Intuitively, the gradient encodes "how each pixel of the input would need to change to reduce the loss", which is a rich, differentiable fingerprint of the input itself. The reconstruction is an optimisation over the input while the network weights are held fixed.

3.2  Design choices (and why)

  • Direction, not magnitude — cosine loss. We match gradients by negative cosine similarity, D(·) = 1 − cos(ĝ, g), rather than Euclidean distance. Cosine matching is magnitude-invariant and far more stable than the original DLG L2 objective, especially as the model trains and gradient norms shrink (Geiping et al., 2020).
  • Total-variation prior. We add α·TV(x̂), the anisotropic total variation of the candidate, which penalises high-frequency noise and pushes the reconstruction toward the piecewise-smooth statistics of natural images.
  • Analytic label recovery (iDLG). The ground-truth label need not be optimised: for single-sample cross-entropy, the class whose row of the final layer's weight-gradient has negative sign is the true label. We read it off directly, which removes a major source of instability.
  • Smooth activations, untrained network. A small LeNet with Sigmoid activations (not ReLU) and a freshly initialised (untrained) network leak the cleanest reconstructions — the easiest, clearest regime for the demonstration, and the honest worst case for the defender.
  • Restarts + group consistency. Reconstruction is seed-sensitive, so we run several random restarts and take a pixel-wise consensus (median) over candidates — the near-free quality trick from GradInversion.

3.3  Workflow

End-to-end attack workflow. Defences act on the gradient in transit and are measured by how much they degrade the server's reconstruction.

6  Preliminary Evaluation, Limitations and Plan for IA-2

6.1  Observations

  • The attack reliably recovers the label (analytic, deterministic) and a high-fidelity image for a single untrained-network sample.
  • Reconstruction quality is seed-sensitive; restarts + median consensus materially stabilise it.
  • Evaluation measures adopted: MSE, PSNR, SSIM (structural) and LPIPS (perceptual) for reconstruction; accuracy/AUC and TPR@low-FPR for membership inference; achieved ε for the DP guarantee.

6.2  Known limitations (to address in IA-2)

  • Single-image regime is the easiest case; batch reconstruction is harder and is being extended (sizes 1→4→8).
  • LeNet has no BatchNorm, so the strongest known prior (BN-statistics matching) is not yet used; a BN variant is planned as an ablation.
  • Defences are evaluated on this model scale; generalisation to deeper networks is discussed, not exhaustively measured.

6.3  Plan for IA-2

  1. Complete the four-defence privacy–utility sweep and the membership-inference DP audit (empirical vs analytical ε).
  2. Cross-validate the hand-written attack against the published breaching framework.
  3. Add the malicious-server contrast (Robbing-the-Fed) analytically.
  4. Assemble the final technical report and an IEEE-format paper draft.
